# Architecture

## Stack

- **TanStack Start** (React 19, file-based routing under `src/routes/`,
  server functions via `createServerFn`)
- **Supabase**: Postgres (RLS-scoped access only — see
  [`DATABASE.md`](./DATABASE.md)), Auth, Storage
- **Tailwind CSS v4** with a hand-built design system (no component
  library beyond a handful of Radix-based primitives in `src/components/ui/`)
- **decimal.js** for every financial calculation (`src/lib/trade-calc.ts`)
- **Zod** for input validation on every server function
- **TanStack Query** for client-side data fetching/caching, one shared
  `QueryClient` per app instance (`src/router.tsx`)
- **Nitro**, `node-server` preset, for the production server build

No charting library, no state-management library beyond TanStack Query, no
component library beyond Radix primitives. This is a deliberate choice, not
an oversight — see [`DECISIONS.md` #16](./DECISIONS.md#d16).

## Routing

File-based, under `src/routes/`. The route tree
(`src/routeTree.gen.ts`) is auto-generated by the TanStack Router Vite
plugin on every `vite build` or `vite dev` — **never hand-edit it**, and if
you add/move/rename a route file, run a build once before trusting any
route-related type error, since the generated tree needs to catch up first.

```
/                       landing page, bounces signed-in visitors to /app
/sign-in                combined sign-in/sign-up, + Google OAuth
/reset-password         password reset request + confirmation
/onboarding             first-run setup (timezone, currency, trader type, first portfolio)
/app                    layout: sidebar nav, portfolio switcher, auth + onboarding gates
  /app                    dashboard: equity curve, open risk, Curated vs. Impulse
  /app/journal            trade table, log/edit modal, CSV import
  /app/analytics          deeper breakdowns, ratio metrics, insight cards
  /app/playbooks          playbook CRUD + trade ideas
  /app/reviews            review queue + weekly/monthly review
  /app/risk-calculator    standalone position-size calculator
  /app/settings           profile, portfolio settings, data export
```

`/app` (`src/routes/app.tsx`) is the only place that decides whether a
visitor gets to see any authenticated page. It:

1. Checks for a session (`supabase.auth.getSession()` + an
   `onAuthStateChange` subscription — not a server-side `beforeLoad`
   redirect, since the session lives in `localStorage` and is only known
   client-side; the actual security boundary is the `requireSupabaseAuth`
   middleware on every server function, not this check).
2. Loads the workspace (`getWorkspace()` — profile + portfolios + active
   portfolio + settings) and redirects to `/onboarding` if
   `profile.onboarding_completed` is false. This is the *only* place that
   redirect happens — see [`DECISIONS.md` #3](./DECISIONS.md#d3).
3. Shows a real error with a retry button if the workspace fails to load,
   rather than an unexplained infinite spinner — see
   [`DECISIONS.md` #24](./DECISIONS.md#d24).

## Server functions

Every read or write to Supabase that isn't the auth session itself lives in
`src/lib/*.functions.ts`, using `createServerFn` + the `requireSupabaseAuth`
middleware. Routes and components never import the Supabase client directly
for privileged data — the one exception is `src/integrations/supabase/client.ts`,
used only for the auth session itself (sign in/out, OAuth, password reset)
and for direct Storage uploads (which go through the browser to Supabase
Storage, then a server function records the resulting metadata row).

`requireSupabaseAuth` (`src/integrations/supabase/auth-middleware.ts`):

1. Verifies the caller's JWT via a **shared, process-wide client** used only
   for `getClaims()` — this client's JWKS cache persists across requests,
   which matters a lot for latency (see
   [`DECISIONS.md` #25](./DECISIONS.md#d25)). It's safe to share because
   `getClaims()` takes the token as an argument rather than reading any
   per-user session state off the client.
2. Builds a **fresh, per-request client** carrying that specific caller's
   bearer token in its headers, and passes it to the handler as
   `context.supabase`. This one genuinely can't be shared — Postgres RLS
   needs to see the right `auth.uid()` for every query, which depends on
   which token is attached.

A typical server function: validate input with Zod, do the read/write with
`context.supabase` (RLS + explicit `owner_id` filters do the access
control — see [`DECISIONS.md` #27](./DECISIONS.md#d27) for when an app-level
ownership pre-check is still worth the extra round trip vs. when it isn't),
return plain data. Errors either bubble up as Postgrest/Postgres errors
translated to a friendly message via `src/lib/db-errors.ts`, or a thrown
`Error` with a specific message for validation-style failures.

## Calculation layer

`src/lib/trade-calc.ts` is the single source of truth for every P&L,
R-multiple, risk, and drawdown calculation in the app. Manual entry, CSV
import, and any future broker sync all funnel through the same functions —
`calculateTrade`, `calculateRiskPreview`, `summarizeClosedTrades` — so the
same inputs always produce the same numbers regardless of entry path.
Everything here uses `Decimal` (decimal.js), never raw JS floats, since
floating-point arithmetic on money is a real source of subtle bugs (e.g.
`0.1 + 0.2 !== 0.3`).

`src/lib/analytics.ts` (Phase 2.3) builds on top of this rather than
duplicating it — every breakdown group's stats come from calling
`summarizeClosedTrades` on that group's trades, so a group of 12 trades and
the whole-portfolio total are computed identically (see
[`DECISIONS.md` #15](./DECISIONS.md#d15)).

**If you're adding a new calculation involving money, R-multiples, or
drawdown: it belongs in `trade-calc.ts`, not inline in a component or route.**

## Client-side data flow

One shared `QueryClient` (`src/router.tsx`), with tuned defaults —
`staleTime: 30_000`, `retry: 1`, `refetchOnWindowFocus: false` — chosen to
make genuine failures surface within about a second instead of several
seconds of silent retrying (see
[`DECISIONS.md` #26](./DECISIONS.md#d26)). Routes and components call
server functions directly as `queryFn`/`mutationFn` — there's no separate
API client layer.

Mutations that change data another already-mounted query depends on call
`queryClient.invalidateQueries(...)` on success. One thing to know before
touching this pattern: if a mutation navigates to a *different* route
immediately after invalidating, and that route reads the same query key,
the invalidation must be **awaited**, not fire-and-forget — otherwise the
new route can mount before the background refetch completes and read the
stale cache. This bit onboarding's finish flow for real; see
[`DECISIONS.md` #29](./DECISIONS.md#d29).

## Design system

`src/styles.css` defines the full token set (`:root` custom properties,
mapped into Tailwind's `@theme inline`) — the "Studio" palette (warm paper and
ink, light and dark themes, cobalt for navigation state; see
[`DECISIONS.md` #1](./DECISIONS.md#d1) and [#48](./DECISIONS.md#d48)) and a handful of custom component
classes (`.surface-panel`, `.modal-panel`, `.metric-value`, etc.) used
throughout instead of a component library. **Never hardcode a color in a
component** — everything should reference a CSS custom property (directly,
or via a Tailwind utility that maps to one) so a future palette change is
one file, not a grep-and-replace across the codebase.

One cascade gotcha worth knowing: custom classes like `.surface-panel` are
defined *after* Tailwind's generated utilities in the compiled stylesheet
(since they're written later in the same source file), so a custom class
that sets a shorthand property (e.g. `.surface-panel { border: 1px solid
var(--color-border); }`) will silently win over a same-specificity Tailwind
utility for a sub-property of that shorthand (e.g. `border-destructive/30`)
applied alongside it. If a Tailwind utility doesn't seem to be taking
effect, this is the first thing to check — an inline `style` attribute
sidesteps it entirely (see `src/components/analytics/InsightCards.tsx` for
an example).

## Error handling philosophy

Two layers, deliberately:

1. **`src/server.ts` / `src/start.ts`**: catch catastrophic SSR failures
   (an exception before Start's handler runs, or h3 swallowing an in-handler
   throw into an opaque 500) and render a static, dependency-free HTML page
   instead of a blank screen or raw stack trace.
2. **Per-query error states**: any `useQuery` whose failure would otherwise
   leave the UI in an ambiguous "still loading?" state should have an
   explicit `.isError` branch with a real message and a retry action. This
   was missing on the workspace-loading path and looked exactly like "the
   app doesn't work" from the outside — see
   [`DECISIONS.md` #24](./DECISIONS.md#d24). Don't reintroduce that gap on
   a new critical-path query.
